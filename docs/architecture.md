# CAMP-I 系统架构设计

## 1. 总体架构

CAMP-I采用经典的DDD (Domain-Driven Design) 分层架构，确保业务逻辑与技术实现解耦。

### 1.1 分层结构

```
┌─────────────────────────────────────────────────────┐
│              Interfaces Layer (接口层)               │
│     CLI / REST API / gRPC / WebSocket / Cron       │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│            Application Layer (应用层)                │
│   Use Cases / Pipeline / Filters / Scorers         │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│              Domain Layer (领域层)                   │
│   Entities / Value Objects / Domain Services       │
│            【零外部依赖的核心业务逻辑】                 │
└─────────────────────────────────────────────────────┘
                         ↑
┌─────────────────────────────────────────────────────┐
│          Infrastructure Layer (基础设施层)           │
│   Gateways / Persistence / HTTP / Messaging        │
└─────────────────────────────────────────────────────┘
```

### 1.2 依赖方向

- 接口层 → 应用层
- 应用层 → 领域层
- 基础设施层 → 领域层（实现领域服务接口）
- 领域层：零外部依赖（依赖倒置原则）

## 2. CAMP-I多因子模型

### 2.1 五维度评估体系

| 维度 | 权重 | 核心逻辑 | 关键指标 |
|------|------|----------|----------|
| Capital Flow (资金面) | 30% | 资金是股价第一推动力 | 主力净流入、连续流入天数、超大单占比 |
| Action (技术面) | 25% | 量价时空关系决定趋势 | 量价配合、换手率、均线排列 |
| Margin (估值面) | 20% | 安全边际与估值保护 | PE/PB、市值规模、股价水平 |
| Plate (板块轮动) | 15% | 顺势而为，跟随热点 | 板块排名、板块资金流、龙头地位 |
| Institution (机构行为) | 10% | 跟随聪明钱 | 龙虎榜、机构买卖、北向资金 |

### 2.2 评分公式

```
总评分 = ∑(因子评分 × 因子权重)

信号映射：
- ≥85分: STRONG_BUY (强买入)
- 75-84分: BUY (买入)
- 60-74分: WATCH (观望)
- 50-59分: AVOID (规避)
- <50分: STRONG_AVOID (强规避)
```

### 2.3 一票否决机制

以下条件任意触发则直接AVOID：
1. 量价背离（涨>3%但主力流出>1000万）
2. 低价股（股价<3元）
3. 亏损小盘股（PE<0且市值<100亿）
4. 机构集体卖出（卖出机构≥3且买入=0）
5. 换手率过高（>30%）

## 3. Pipeline设计

### 3.1 四阶段流水线

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│  Fetch   │────▶│  Filter  │────▶│  Score   │────▶│ Analyze  │
│ 数据采集  │     │ 策略过滤  │     │ 多因子   │     │ AI分析   │
│  (并发)   │     │  (规则)   │     │  评分    │     │  (限流)   │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
     │                │                 │                 │
     ▼                ▼                 ▼                 ▼
[背压控制]        [去重缓存]        [权重计算]        [熔断器]
[限流器]          [Redis/LRU]       [因子归一化]      [令牌桶]
```

### 3.2 并发模型

- **Fan-out**: 多个Worker并发处理Analyze阶段
- **Channel**: 使用带缓冲的channel传递数据
- **Context**: 统一的超时和取消控制
- **ErrGroup**: 优雅的错误处理和同步

## 4. 风控体系

### 4.1 六层风控

```
1. 信号级风控
   ├─ 置信度检查（≥60%）
   ├─ 一票否决条件
   └─ 信号降级（大盘环境）

2. 仓位级风控
   ├─ 单股限制（≤15%）
   ├─ 板块限制（≤30%）
   └─ 总仓位（≤85%）

3. 账户级风控
   ├─ 日亏损限制（5万或5%）
   ├─ 周亏损限制（10%）
   └─ 月亏损限制（20%）

4. 动态风控
   ├─ 连续亏损（≥3次触发冷却）
   └─ 市场降级（大盘跌>2%）

5. 止损止盈
   ├─ 固定止损（3-8%）
   ├─ 移动止损（盈利10%启动）
   └─ 时间止损（最长30天）

6. 异常检测
   ├─ 诱多陷阱
   ├─ 妖股识别
   └─ 流动性风险
```

## 5. 韧性设计

### 5.1 限流器（Token Bucket）

```go
type TokenBucket struct {
    rate   float64  // 每秒生成token数
    burst  int      // 最大token数
    tokens float64  // 当前token数
}
```

应用场景：
- 数据源API调用（10 QPS）
- AI API调用（0.5 QPS = 30 RPM）

### 5.2 熔断器（Circuit Breaker）

三态模型：
- **CLOSED**: 正常状态，请求通过
- **OPEN**: 熔断状态，拒绝请求
- **HALF_OPEN**: 半开状态，尝试恢复

触发条件：
- 连续失败≥5次 → OPEN
- 超时60秒 → HALF_OPEN
- 成功3次 → CLOSED

### 5.3 重试机制

指数退避 + 抖动：
```
delay = base_delay * (2 ^ attempt) + random_jitter
```

## 6. 可观测性

### 6.1 三大支柱

**1. Logging (日志)**
- 结构化日志（JSON格式）
- 分级别（DEBUG/INFO/WARN/ERROR）
- 关键路径埋点

**2. Tracing (链路追踪)**
- TraceID贯穿请求全生命周期
- 记录每个阶段耗时
- 关联日志和指标

**3. Metrics (指标)**
- 系统指标：CPU、内存、goroutine
- 业务指标：信号数、评分分布、成本
- 性能指标：延迟、吞吐量、错误率

## 7. 成本优化

### 7.1 AI成本控制

目标：单次<¥0.3，日<¥100

策略：
1. **Prompt优化**: 简洁精准，控制在1000 tokens内
2. **缓存机制**: 相同股票1小时内复用结果
3. **批处理**: 合并相似请求
4. **分级策略**: 预评分<60的不调用AI

### 7.2 存储成本

目标：<¥500/月

策略：
1. **TimescaleDB**: 时序数据高效压缩
2. **数据保留**: 原始数据30天，聚合数据1年
3. **Redis缓存**: 热数据1小时TTL

## 8. 扩展性

### 8.1 水平扩展

- **无状态设计**: 所有组件无状态，可随意扩展
- **负载均衡**: Nginx/K8s Service
- **消息队列**: Kafka解耦生产消费

### 8.2 垂直扩展

- **Worker数量**: 根据CPU核心数调整
- **Channel缓冲**: 根据内存调整
- **批次大小**: 根据吞吐量调整
